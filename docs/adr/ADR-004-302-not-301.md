# ADR-004 — Serve 302 Found, not 301 Moved Permanently

**Status:** Accepted
**Decision owner:** engineer (me).

## Context

A shortener can answer with either. 301 is the "correct" semantic — the short URL does permanently
stand for the long one — and it is dramatically cheaper: browsers and intermediaries cache it, so
repeat visits never reach our service.

## Decision

302, on every redirect.

## Why

Two properties we committed to are incompatible with a cached redirect:

1. **Analytics.** A cached 301 means the second and subsequent clicks never touch our service. Click
   counts would silently under-report by an unknowable factor, which is worse than not offering
   analytics at all.
2. **Revocation.** `DELETE /api/v1/links/{code}` has to actually stop the redirect. With a 301 in a
   user's browser cache, a link that has been disabled — potentially because it was reported as
   malicious — keeps working for that user indefinitely, and we have no way to reach into their
   cache.

The second reason is the decisive one. An abuse-response mechanism that some users can ignore is
not an abuse-response mechanism.

## Consequences

- We serve every click, so redirect traffic scales with usage rather than with unique users. The
  two-tier cache exists largely to make that affordable.
- Marginally slower for repeat visitors than a cached 301 would be.
- If a deployment ever values edge cacheability over analytics and revocation, this becomes a
  per-link option — but it must be an explicit choice with those consequences spelled out, not a
  default.
